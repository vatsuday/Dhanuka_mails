# Spike S0.7: BullMQ 6 on Valkey

**Date:** 2026-10-15 · **Story:** S0.7 · **Decision recorded in:** [ADR-004](../adr/ADR-004-queues-cache-scheduling.md)
**Versions:** BullMQ 6.3.10, ioredis 6.0.0 (BullMQ 6 takes ioredis as a peer dependency, so the app and BullMQ share one copy), Valkey 8.1.10, Node 26.4.0.
**Evidence:** `apps/worker/test/integration/bullmq-spike.test.ts` and `tenant-sample.test.ts`, run on Testcontainers in CI on every push. Locally: 10/10 passed three runs in a row (Windows, Docker Desktop).

## Question

ADR-004 chose BullMQ 6.3.x, with 5.x as the fallback if the spike found problems with retries, delayed jobs, repeatable jobs, stalled-job recovery or Valkey compatibility.

## Results

All tests ran against Valkey configured exactly like `valkey-queue` in `infra/docker/docker-compose.yml` (`--appendonly yes --appendfsync everysec --maxmemory-policy noeviction`).

| Behaviour | Result | How it was tested |
|---|---|---|
| Retry with backoff | ✅ | `attempts: 3`, exponential backoff 300 ms. Attempts were ≥ 300 ms and then ≥ 600 ms apart, and the third attempt completed (`attemptsStarted` = 3). |
| Exhausted retries | ✅ | `attempts: 2`, always failing: the job ends in `failed` with its `failedReason`. |
| Delayed jobs | ✅ | `delay: 800`: state is `delayed` straight after `add`, and `processedOn - timestamp` ≥ 800 ms. |
| Repeatable jobs | ✅ | `upsertJobScheduler('tick', { every: 300 })` ran at least 3 times in 1.6 s. Upserting the same ID twice leaves one scheduler. After `removeJobScheduler` no further runs happened. |
| Stalled-job recovery after the worker is killed | ✅ (see finding 1) | A separate Node process took the job and was killed with `SIGKILL` mid-job. A healthy worker emitted `stalled`, moved the job back to waiting and completed it; `stalledCounter` = 1. |
| `noeviction` on valkey-queue | ✅ | The setting is `noeviction` with AOF on. With `--maxmemory 3mb`, adding 32 KB jobs eventually failed with an `OOM` error, and **every job already accepted was still queued**. Under an evicting policy those jobs could vanish silently. |
| Valkey compatibility | ✅ | No errors or warnings from BullMQ against Valkey 8.1.10. |
| Tenant job inside `withTenant` (AC 4) | ✅ | The `tenant-sample` worker counts the job tenant's active contacts as `app_user` through `withTenant`. It returned 2 for tenant A (2 active, 1 soft-deleted), 5 for tenant B, 0 for an empty tenant, and failed a job with a non-UUID tenant ID before querying. Also run once end to end with the real `apps/worker` process against the local Docker stack. |

## Findings

1. **Every worker on a queue must use the same `stalledInterval`.** BullMQ throttles stalled-job checks with a `stalled-check` key whose TTL is the `stalledInterval` of whichever worker set it last. In the first run, the killed worker had the default 30 s interval and the recovering worker had 500 ms. The job then stayed `active` well after its lock had expired, because the faster worker's checks were skipped until the key expired. **Rule:** worker timing options come from one shared constant per queue, never set per process.
2. **Recovery time is roughly `lockDuration` + up to 2 × `stalledInterval`** (the first check marks a job, the next one moves it). With BullMQ's defaults (30 s each) a crashed worker's job can wait about 90 s. This is acceptable because ADR-004 already makes Postgres the source of truth: the reconciler re-enqueues stalled campaigns, and sending leases expire `sending → unknown`. Shorter settings can be chosen per queue when a story needs faster recovery.
3. **Job processors need their own connection with `maxRetriesPerRequest: null`** (`apps/worker/src/queue.ts`). The readiness check keeps its fail-fast client, so `/ready` still fails quickly when Valkey is down.
4. **Shutdown:** `worker.close()` waits for active jobs. When Valkey is unreachable, the worker app force-closes so SIGTERM cannot hang.
5. **`maxStalledCount` defaults to 1:** a job that stalls twice is failed, not retried forever. Jobs must be idempotent anyway (outbox `jobId = outbox.id`, ADR-004).

## Decision

**Keep BullMQ 6.3.x** (6.3.10 pinned). None of the fallback triggers in ADR-004 occurred, so 5.x is not needed.

## Not covered by this spike

- ElastiCache-specific behaviour (failover, Multi-AZ, memory alarms). Covered when staging is provisioned.
- Throughput and Lua token-bucket throttling (ADR-004 §4). Covered with the sending pipeline stories.
- BullMQ's PostgreSQL backend (new in 6.x). Not evaluated; Valkey remains the queue store.
